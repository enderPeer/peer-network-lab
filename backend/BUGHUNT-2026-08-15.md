## CRITICAL

### A funded but not-yet-posted unsecured handle can be seized by any stranger, who both locks the owner out and spends the reserve the owner destroyed real bitcoin for

**Status:** FIXED in 198bc78  
**Flow:** REGISTRATION & LOGIN — every path by which an identity is cr  
**Where:** webapp/server.mjs:1464 (SUBSTANTIVE set), server.mjs:1465-1469 (hasHistory), server.mjs:2454-2472 (authError setPin branch), server.mjs:2423 (btcBurn actor derived from act.id)

**Repro:** 1) Register a handle with NO pin (allowed; onboarding even tells new users to burn bitcoin as step 2 before it stresses a PIN). 2) Acquire reserve: a verified btcBurn credits energy to the handle. 3) Before the owner ever posts, a stranger who knows the id sends POST /api/act {"t":"setPin","id":"u_victim","pinHash":"<sha256(id:9999)>"} with no auth. Demonstrated on a local scratch host built from server.mjs: fixture u_nopin (registered, btcBurn of 100000 sats, energy=1000, no posts). Stranger setPin -> HTTP 200 ACCEPTED. Then POST /api/v1/post {as:u_nopin, pin:9999, text:...} -> 200: the stranger now posts spending the victim's burned reserve. The owner, who never had a PIN, is now locked out and cannot recover except via the operator.

**Expected:** hasHistory() must treat a handle that holds reserve (a completed btcBurn) as claimed, so setPin from an unauthenticated stranger is refused with HANDLE_UNCLAIMABLE — the same protection given to a handle that has posted. Reserve represents destroyed bitcoin and epoch-earning capacity; it is exactly the value the PIN_REQUIRED/bindAddress logic already treats as worth protecting.  
**Actual:** hasHistory() only scans SUBSTANTIVE = {post,review,opinion,tag,dm,stream,call,event,market}. btcBurn / burn / deposit / follow / profile / bindAddress are absent, and btcBurn carries its actor in `id` (not author/from) anyway, so a handle that has ONLY registered and burned reserve returns hasHistory=false. authError's setPin branch (server.mjs:2465) then falls through and accepts a first PIN from anyone — handing the account and its reserve to whoever sets a PIN first. This is the exact 'whoever set a PIN first owned the name' takeover the comment at server.mjs:2458-2464 claims to have closed, still open for the funded-silent window.

**Fix hint:** Add the reserve-bearing acts (btcBurn/peerBurn/burn/deposit) to what hasHistory() counts, or gate the first setPin on 'has this handle ever received reserve OR spoken'. Equivalently, refuse a stranger's first setPin on any handle whose ledger burnBal > 0.

### Credential indexes are built once at boot: a mirror (and a mirror the election promotes) accepts acts for PIN-secured handles with no/wrong PIN, and refuses the real owner

**Status:** FIXED in 198bc78  
**Flow:** MIRRORS / ELECTION / OFFLINE: host.json probe order, client   
**Where:** webapp/server.mjs:1352-1373 (pinIndex/keyIndex/recoveryIndex built from `acts` once), :634 and :601-607 (mirrorSync/mirrorAdopt push acts without indexing), :839-849 (promoteSelf rebuilds nothing), :2454-2472 (authError waves through a handle with no index entry), :369 (deletedIds also boot-only)

**Repro:** 1) Spawn a primary whose log has {t:'register', id:'u_secured', pinHash:...} + burns. 2) Spawn a mirror from an EMPTY acts.jsonl (the pattern tests/host.test.ts:353 documents) with PEER_MIRROR_OF=<primary>, PEER_FEDERATION=<primary>, PEER_ELECTION_INTERVAL=2000, PEER_PROMOTE_AFTER=2. 3) Wait until /api/acts totals match. 4) POST <mirror>/api/signal/poll {who:'u_secured', auth:''} -> 200 {signals:[]} (primary answers 401). 5) Kill the primary; wait for '[election] PROMOTED'. 6) POST <mirror>/api/act {t:'post', author:'u_secured', text:'forged', a:0.5} with no auth -> 200; with auth:'0000' -> 200. 7) POST bindAddress for u_secured with the CORRECT pin '1234' -> 401 PIN_REQUIRED 'this handle has no PIN and no passkey'. Script used: scratchpad/repro-mirror-index.mjs.

**Expected:** Any host that answers a write or a mailbox poll enforces the credentials the log declares: 401 without the PIN, 200 with it, and a rotated PIN (setPin synced later) invalidates the old one.  
**Actual:** On a mirror, every register/setPin/setKey/setRecovery/deleteAccount that arrives via sync is invisible to authError. After automatic promotion (the designed path — no restart), anyone can post/dm/react/follow as any handle registered or re-PINned since the mirror booted (a mirror started empty: EVERY handle); old PINs remain valid after rotation; deleted accounts can act again; the legitimate owner is refused PIN_REQUIRED acts (bindAddress/profile/deleteAccount) and told to 'secure it', and setPin on a handle with history is operator-only, so they are locked out while an attacker is not. Even before promotion the mirror's /api/signal/poll hands anyone any handle's call mailbox and /api/auth/challenge lists stale passkeys.

**Fix hint:** Factor the boot index build into rebuildIndexes() (pinIndex, keyIndex, recoveryIndex, deletedIds) and call it after every mirrorSync append/adopt and in promoteSelf/demoteTo; or index each synced act the way applyActInner does.

**Expected:** Opening a relay for content id `cid` should require that the caller authored the stream act that minted `cid` (or at least that `cid` is one of the caller's own stream nodes), so a broadcast attributed to a handle can only be produced by that handle — which is exactly the property the STREAM_NEEDS_PIN check at server.mjs:5369-5375 says it is protecting ('a stream puts a face and a voice on a name, and nothing afterwards could show it was not the owner').
